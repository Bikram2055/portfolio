A multi-tenant SaaS used by yacht charter brokers and fleet managers. It covers fleet data, brochures, bookings, leads, billing, websites and a partner API. I own most of the backend: about 1,000 of the platform's 1,600 commits.

Claude extracts structured yacht data under a concurrency limit and an image-token budget, and validated results are applied back to the fleet. Bulk descriptions are generated through the OpenAI Batch API with output validation.
  • Partner API and scale. API-key auth, per-request logging middleware, date-range pricing, Elasticsearch with accent-insensitive search, and Locust load tests at 1,000 requests per second before launch.
02

Sole engineer · client 2025 ↗
Insurance · Legal billing02
6k+
claims clustered & audited

For a motor-accident insurance client in Australia, I built an AI pipeline that audits law-firm invoices against billing guidelines. It flags violations and estimates potential savings across thousands of claims.

  • A staged pipeline instead of one giant prompt. It clusters claims, generates phase-wise guidelines, tags each line item with phase and activity codes, then runs qualitative review, violation detection and savings estimates.
  • LLM output treated as untrusted input. Structured results come through function-calling with retries and timeouts, plus JSON-repair fallbacks. LiteLLM keeps the system provider-agnostic.
  • Embedding-based clustering of 6,000+ claims. Guidelines are generated once per group rather than once per claim, which cuts cost and keeps rulings consistent.
  • Long jobs off the request path. Clients start a run and poll a task ID while Celery and Redis do the work.
  • Prompts treated like code. Prompts are versioned with an evaluation set, alongside a written analysis of cost, scaling and monitoring.

A scraping and validation platform that keeps a yacht catalogue accurate across many outside sources. The goal: bad data must never reach production silently.

  • Staging first, one way in. Scraped data lands in a staging schema. A single promotion service is the only path into production, and every promotion writes an audit row.

(02) How I work

How I solve problems

Principles I've learned shipping real systems, and what they mean for your product.

  1. 01

    Make the failure mode boring.

    Bad data, retries and partial failures are designed for from day one. That means staging before production, idempotent jobs, audit trails and a single promotion path. Your system degrades quietly instead of failing loudly at 2 a.m.

  2. 02

    Treat LLM output as untrusted input.

    Structured outputs, validation, repair and retries; prompts versioned with evaluation sets; costs budgeted before launch. AI features you can actually put in front of customers.

  3. 03

    Isolate what must never leak.

    Schema-per-tenant databases, migrations kept separate for shared and tenant data, and API keys with request logs. Tenants and partners can't see each other's data, by design rather than by convention.

  4. 04

    Keep slow work off the request path.

    Long LLM jobs, document extraction, billing cycles and campaigns run in queues and batch APIs that users poll. The product stays fast while the heavy work happens in the background.

  5. 05

    Measure, then scale.

    I load-test before launch (1,000 req/s on YC Suite) and trace with Sentry and Langfuse. Decisions are based on numbers, not guesses about where the bottleneck is.

  6. 06

    Write the decision down.

    Architecture decision records, specs and approach documents. The next engineer, or your team, can see why the system looks the way it does.
